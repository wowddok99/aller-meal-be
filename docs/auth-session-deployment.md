# 로그인 상태 유지 인증 배포 절차

이 절차는 신규 로그인 선택값과 Refresh Token 패밀리 정책을 사용하는 버전을
배포할 때 적용합니다. `rememberMe`를 생략하거나 `null`로 보내는 기존 클라이언트와
기존 토큰은 기존 정책을 유지합니다. 명시적인 `true` 또는 `false`로 만든 세션은
14일 sliding 만료와 로그인 시점부터 30일 절대 만료를 적용합니다. 로그아웃은
Refresh Token을 폐기하며 이미 발급한 Access Token은 만료까지 유효합니다.

## 전환 전제

- 구버전 서버는 `rememberMe`를 무시하므로 새 FE를 먼저 노출하거나 인증 요청을
  구·신버전에 나누어 보내면 선택한 쿠키 및 절대 만료 정책이 보장되지 않습니다.
- 신규 패밀리의 보호된 `sessionVersion`은 구버전 refresh에서 거부됩니다. 해당
  요청은 세션을 폐기하므로 이 보호는 혼재 배포의 가용성을 보장하지 않습니다.
- 보호 형식 도입 전에 발급된 숫자형 신규 패밀리는 구버전 refresh에서 정책이
  무시될 수 있습니다. 신버전에서 정상 회전하면 보호 형식으로 전환됩니다.
- 배포 대상의 ingress, 직접 접근, 내부 호출 및 대체 경로를 모두 확인합니다.
  구버전 인증 경로가 하나라도 남거나 요청 drain을 확인할 수 없다면 새 FE 기능을
  노출하지 않습니다. 이 저장소의 로컬 Compose는 운영 라우팅을 정의하지 않으므로
  실제 인프라의 전환 가능 여부를 증명하지 않습니다.

## 안전한 전환

1. 새 FE 기능을 비활성 상태로 유지합니다. 새 API를 직접 호출하는 클라이언트도
   고려해, 필요한 경우 모든 외부·내부 인증 진입점에서 로그인과 refresh를 일시
   차단합니다. 로그인만 차단하거나 FE만 숨기는 것으로 충분하지 않습니다.
2. 구버전으로 새 요청이 유입되지 않도록 모든 경로를 차단하고 진행 중인 로그인과
   refresh를 완료 또는 종료시켜 drain합니다. 재시도, 유지 연결, 직접 접근 및
   우회 경로도 포함합니다. 차단과 drain 여부는 실제 라우터 및 인스턴스 관측으로
   확인합니다.
3. 정책을 강제하는 신버전을 모든 인증 경로에 배치합니다. 신버전만 로그인과
   refresh를 처리하는지, Redis와 쿠키 보안 설정이 올바른지 확인한 뒤 인증 요청
   차단을 해제합니다. 기존 토큰의 정상 refresh도 확인합니다.
4. 그 후에만 새 FE 기능을 노출합니다. 구버전으로 인증 요청이 다시 유입되지
   않도록 배포·자동 확장·장애 복구 설정에도 동일한 제한을 유지합니다.

## 롤백

- 권장 방법은 로그인과 refresh를 정책 강제 신버전으로 계속 처리하면서 나머지
  구성만 롤백하는 것입니다. 모든 인증 경로에 대한 라우팅과 우회 차단을 유지하고,
  롤백 후에도 CSRF, rotation, 재사용 감지와 폐기 경로를 확인합니다.
- 구버전 인증 서버를 복원해야 한다면 우선 로그인과 refresh를 차단하고 모든
  진행 요청을 drain합니다. 정책 적용 세션이 더는 구버전으로 도달할 수 없다는
  근거가 없으면 구버전 인증을 열지 않습니다. 신규 세션 발급을 완전히 중단한
  시점부터 절대 만료가 지난 것을 확인하는 방법은 구버전이 해당 세션을 한 번도
  정책을 무시한 채 회전하지 않았다는 근거가 있을 때만 유효합니다. 시계 오차와
  진행 요청도 고려합니다.
- 이미 구버전이 숫자형 신규 패밀리를 회전했을 가능성이 있다면 30일 대기만으로
  해결되었다고 판단하지 않습니다. 영향 세션을 식별하고 정상적인 폐기 절차를
  마련하거나 정책 강제 인증 서버를 유지해야 합니다. 세션 폐기는 사용자에게
  재로그인을 요구하므로 별도 운영 판단이 필요합니다. Redis 전체 삭제 또는
  무차별 세션 삭제로 대체하지 않습니다.

이 문서는 전환 조건과 순서입니다. 실제 운영 경로, drain, 데이터 존재 여부,
배포 및 롤백은 해당 환경에서 별도로 확인해야 합니다.
